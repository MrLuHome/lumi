# ROUND 9 — 安全复审

- 日期：2026-11-21
- 范围：本轮新增/修改的数据完整性代码、ONNX Worker、评测导出 CLI、发行资源打包、诊断日志
- 方法：逐文件人工复核 + 现有自动化测试（`cargo test` 431 passed / `npm test` 65 passed）+ GUI 验收
- 结论：未发现新的可远程利用漏洞；存在若干已记录的**本地**风险与未验证边界

## 1. 数据完整性（项目文件）

| 检查点 | 结果 | 说明 |
| --- | --- | --- |
| 加载期默认参数覆盖真实值 | 已修复 | `commit`/`apply` 在非 `ready` 阶段拒绝写入；人脸恢复按 UUID 合并 |
| 保存侧静默删除数据 | 已修复 | `merge_saved_faces` 按 UUID 合并，保留 dense/level3 与未检测记录 |
| 首次保存前备份 | 已实现 | 写 `.lumi.bak` 后再原子替换，回读校验 |
| 损坏项目静默降级 | 已避免 | 解析失败 → `failed` 阶段 + 明确错误，不生成空项目 |
| 项目 ID / 源图哈希校验 | 已实现 | `computeProjectId`（SHA-256 前 16 字节）+ `sourceHash` |
| 跨项目串数据 | 已防护 | `requestId` 守卫 + 提交前 `projectId` 校验 |
| 路径穿越 | 不适用 | 路径来自本地文件对话框，据此打开用户选择的文件；无网络输入 |

残余风险：

- `.lumi.bak` 只在保存时生成一次，连续两次异常保存可能覆盖更早的备份；
- 项目文件无签名，恶意构造的 `.lumi` 仍可让 JSON 解析失败（会报错，不会执行代码）。

## 2. ONNX Worker 隔离

| 检查点 | 结果 |
| --- | --- |
| 用户模型是否在主进程加载 | 否：`--face-model-probe` / `--face-model-infer` 子进程 |
| 输入/张量/输出上限 | 1024 边长、3,145,728 元素、512 MiB 模型、输出长度受限 |
| 超时 | 探针 20 s、推理 10 s，超时 kill |
| 资源限制 | `RLIMIT_AS` 1.5 GiB、`RLIMIT_CPU` 10 s（仅 Unix） |
| IPC | 临时文件 JSON，stdout/stderr 丢弃，不拼接 shell |
| 异常 | 损坏/未知算子/维度错误/NaN/越界/超时/崩溃均有测试覆盖，主进程存活 |
| 能力等级 | RuntimeTested 不解锁 LEVEL 3，导入后仅「可用」 |

**未验证/不宣称**：

- 未做完整沙箱（无 seccomp/App Sandbox/容器），子进程仍以当前用户身份运行，
  可读取该用户有权访问的文件；`RLIMIT` 只限制内存与 CPU 时间；
- Windows 无 `RLIMIT` 等价实现，Worker 限制未验证；
- 临时请求文件位于系统临时目录，未加密。

## 3. 评测导出 CLI（`--nme-predict`）

- 只读本地清单中的照片，写出一份 JSON；不联网、不上传、不写项目文件。
- 清单可指定任意本地路径，等同用户主动运行一个本地工具，无提权。
- 输出包含人脸坐标（生物特征衍生数据），仅落在用户指定路径；未默认写入仓库。
- 建议：发行版可考虑改为独立开发工具，避免普通用户误触；本轮保持现状并记录。

## 4. 诊断日志与隐私

- 仅 `import.meta.env.DEV` 下输出，发行版静默。
- 记录：`requestId`、项目 ID、阶段、计数、耗时、错误码。
- 不记录：照片内容、关键点坐标、模型权重、完整个人路径（路径只保留文件名）。
- 修复：`load_failed` 不再写入完整错误文本，避免 serde 错误带出绝对路径。
