## 1. 验收中发现的 P0 缺陷与修复

| # | 现象 | 根因 | 修复 | 证据 |
|---|---|---|---|---|
| 1 | 正式包启动后整窗纯黑，AX 树只有 1 个空 `AXGroup` | `tauri.conf.json` 的 CSP 为 `script-src 'self'`，自定义协议 `tauri://localhost` 下所有脚本被拦截 | CSP 显式允许 `tauri:` / `http://tauri.localhost` / `ipc:`，其余保持收紧 | `00-blank-before-fix.jpg`、`01-launch-fixed.jpg` |
| 2 | 界面出现后画布空白，照片被推到视口外（`.stage` 高 6626px，`.stage-frame` 在 y=2849） | `.inspector` / `.inspector-body` 缺少 `min-height: 0`，长面板把 grid 行撑高 | 两个类补 `min-height: 0` 与 `overflow: hidden/auto` | 修复后 `.stage` 878×818、首屏可见（`02-resized.jpg`） |
| 3 | 前端抛 React error #185（Maximum update depth） | `ReshapePanel` 的 Zustand 选择器每次返回新 `[]`，快照不稳定 | 改为模块级常量空数组 | 浏览器复现与修复后对比 |
| 4 | 批量处理时新旧照片同时驻留，峰值内存翻倍风险 | 批量线程缓存无上限、载入新图前不释放旧图 | 批量专用缓存预算 256 MB + 每张开始前 `ImageCache::clear()` | 见 `ROUND6_MEMORY_OPTIMIZATION.md` |

## 3. 环境限制与残余风险

- 正式包运行在 App Sandbox 下，`/tmp` 对应用只读（`Read-only file system (os error 30)`）。批量输出目录必须选用户可写目录（本次使用 `~/Documents/lumi-batch-out`）。这属于平台沙盒行为，不是缺陷；已在验收记录中保留原始报错。
- 未加载照片时，预设库缩略图为占位灰块（缩略图依赖当前照片预览），属于外观问题，不影响应用/导出。
- 第 20、21 项未通过 GUI 触发，按规则**不计为通过**；其能力由自动化测试覆盖，但本轮不宣称已完成 GUI 验收。

## 4. 结论

第六轮正式包在真实 GUI 下可完成“导入—调整—智能分析—预设—批量导出—项目保存/恢复”的完整闭环；本轮修复的 4 个缺陷均已在重建后的正式包上复验。除第 20、21 项外，spec §3.1 清单全部有可复核截图证据。
